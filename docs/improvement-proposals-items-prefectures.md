# エンドポイント改良提案: `/prefectures` と `/items`

最初からある `GET /prefectures` と `GET /items/{prefecture}/{datehour}` について、機能追加・名称改善・レスポンス構造の案をまとめます。

---

## 1. `GET /prefectures`

### 現状

- **レスポンス**: 都道府県 ID の配列のみ  
  `["hokkaido", "aomori", "iwate", ...]`
- **用途**: `/items/{prefecture}/{datehour}` の `prefecture` に使う ID の確認

### 提案

#### 1.1 レスポンスの拡張（推奨）

ID だけでなく、UI で使いやすいメタ情報を付与する。

**案 A: オブジェクト配列で返す（後方互換は別エンドポイント or クエリで維持）**

```json
[
  { "id": "hokkaido", "name_ja": "北海道", "has_data": true },
  { "id": "aomori", "name_ja": "青森県", "has_data": true }
]
```

- `name_ja`: 日本語の都道府県名（`stations_loader.PREF_NAME_TO_ID` の逆引きで生成可能）
- `has_data`: 当該県が `prefecture_retrievers` に含まれるか（API で実際にデータ取得可能か）

**案 B: 従来の配列は維持し、詳細は別エンドポイントで**

- `GET /prefectures` → 従来どおり `["hokkaido", "aomori", ...]`（変更なし）
- `GET /prefectures/detail` または `GET /prefectures?detail=1` → 上記オブジェクト配列を返す

クライアントの破壊を避けつつ、必要なら詳細を取れるようにする。

#### 1.2 地域ブロックの付与（任意）

ダッシュボードなどで「東北」「関東」でまとめて表示したい場合に便利。

```json
{ "id": "miyagi", "name_ja": "宮城県", "has_data": true, "region": "東北" }
```

- `region`: 北海道・東北・関東・中部・近畿・中国・四国・九州・沖縄 などの定数マップを API 側で持つ

#### 1.3 名称について

- パス `/prefectures` はそのままで問題ない（都道府県一覧であることが明確）。
- レスポンスのキー名は `id` を採用すると他エンドポイント（`stations` の `station_id` など）と揃えやすい。

---

## 2. `GET /items/{prefecture}/{datehour}`

### 現状

- **パス**: 都道府県 ID と ISO8601 日時（正時に丸め、1 時間フォールバックあり）
- **レスポンス**:
  - `data`: 各カラムが「行番号（0, 1, 2, …）→ 値」の辞書
  - `spec`: 測定項目ごとの単位・説明・型

行番号ベースのため、クライアントは「局コード ↔ 行」の対応を自分で組み立てる必要がある。

### 提案

#### 2.1 レスポンス構造の改善（推奨）

**案 A: 局単位の配列形式を選べるようにする**

クエリで `format=by_station` などを指定したときのレスポンス例:

```json
{
  "target_datetime": "2024-09-03T06:00:00+09:00",
  "data": [
    {
      "station_id": "13114010",
      "observed_datetime": "2024-09-03T06:00:00+09:00",
      "PM25": 12.0,
      "OX": 28.5,
      "NO2": 8.0
    },
    {
      "station_id": "13114510",
      "observed_datetime": "2024-09-03T06:00:00+09:00",
      "PM25": 15.3,
      "OX": 30.1,
      "NO2": 6.5
    }
  ],
  "spec": { ... }
}
```

- 局ごとにオブジェクトが並ぶため、フロントでのループ・表示・フィルタがしやすい。
- 既存の「行番号→値」形式は `format=legacy` またはクエリなしで維持し、後方互換を保つ。

**案 B: 既存形式のまま「実際に採用した時刻」だけ追加**

フォールバック時に「どの時刻のデータを返したか」を明示する。

```json
{
  "target_datetime": "2024-09-03T06:00:00+09:00",
  "actual_datetime": "2024-09-03T05:00:00+09:00",
  "data": { ... },
  "spec": { ... }
}
```

- `actual_datetime`: 実際に DB から返した `target_datetime`。フォールバック時は要求より 1 時間前になる。

#### 2.2 機能追加

- **取得項目の限定**  
  `?items=PM25,OX,NO2` のように指定した項目だけ `data` に含める。  
  通信量削減・フロントの扱い簡略化に有効。

- **採用時刻の明示**  
  ［上記 2.1 案 B のとおり］ レスポンスに `actual_datetime`（および必要なら `target_datetime`）を含める。

- **複数時刻の一括取得（将来案）**  
  `?hours=3` や `?from=...&to=...` で複数正時を一度に返す。  
  実装コストが大きい場合は、既存の「1 リクエスト＝1 時刻」を維持し、`/timeseries` など別エンドポイントに任せる選択肢もある。

#### 2.3 測定項目メタの分離（任意）

- 現在は `spec` が毎回同じ内容で付いてくる。
- `GET /items`（パスパラメータなし）を「測定項目仕様の一覧」専用エンドポイントにすると:
  - クライアントは初回だけ `/items` で仕様を取得し、以降は `/items/{prefecture}/{datehour}` で `data` のみ受け取る運用ができる。
- 既存の `/items/{prefecture}/{datehour}` の `spec` は、省略可能にするかそのまま付与するかはポリシー次第。

#### 2.4 名称について

- **パス `/items`**  
  「測定項目」というより「ある時点の測定値」に近い。  
  - 意味を明確にする候補: `/measurements`, `/hourly`, `/data` など。  
  - 変更すると破壊的になるため、新バージョンや別パス（例: `/v2/measurements/{prefecture}/{datehour}`）で検討するのが無難。

- **レスポンスの `data` / `spec`**  
  そのままで分かりやすい。  
  - 局配列形式を導入する場合は、`data` が配列になる旨を OpenAPI と README で明記する。

## 3. 実装の優先度の目安

| 優先度 | 内容 | 理由 |
|--------|------|------|
| 高 | `/prefectures` に `name_ja`（＋必要なら `has_data`）を追加 | 実装が軽く、UI でそのまま使える |
| 高 | `/items` レスポンスに `actual_datetime`（と `target_datetime`）を追加 | フォールバック時の挙動が明確になる |
| 中 | `/items` に `format=by_station` で局単位配列を返すオプション | クライアント実装が簡潔になる |
| 中 | `/items?...&items=PM25,OX` で取得項目の限定 | 転送量削減・利用しやすさ向上 |
| 低 | 地域ブロック `region`、`GET /items` で spec 専用、パス名の変更 | 必要に応じて検討 |

---

## 4. まとめ

- **`/prefectures`**: 現状の「ID の配列」に加え、日本語名と（必要なら）データ取得可否を返す形にすると、そのまま UI やドロップダウンに使え、改良効果が大きい。
- **`/items/{prefecture}/{datehour}`**:  
  - まずは「採用した時刻」の明示（`actual_datetime` / `target_datetime`）を追加し、  
  - 余力があれば「局単位の配列」形式と「取得項目の限定」をクエリで選べるようにすると、使い勝手と一貫性が両立しやすい。

既存クライアントを壊さない範囲では、クエリパラメータや新形式の追加で対応し、パス名の変更は v2 や別パスで検討するのが安全です。
